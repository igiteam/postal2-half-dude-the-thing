This is the full PS2 game disc structure. Let me lay out what's actually there and where the Digimask code lives.

🎯 The Important Files for Your Goal
The main executables:

SCES_524.26 — the main game ELF (UK/EU region). This is the most important file. All the Cameo logic lives here, calling into the IOP modules and processing the photos.

SCES_525.01 — a secondary ELF, probably a regional variant or update. Start with SCES_524.26.

The Digimask-specific modules:

CAMEO/MODULES/ — this is the Cameo-specific IOP module set. It's a separate directory from MODULES/, which means the Cameo system is a self-contained subsystem.

EYETOY.IRX — the EyeToy camera driver.

SCRM202.IRX — a cryptographic module (SCRM = "scramble" or "secure scramble"). This is likely what does the XOR/zlib work.

MEM2MB.IRX — memory expansion module for handling large buffers (the head model is ~786 KB, so needs extra heap).

USBD.IRX — USB driver, needed for the EyeToy.

MSTR71.IRX — probably "MegaStreamer 71" or similar; audio or stream-related.

The data files:

DATA.ZIP — the archive that contains Launchpad/Data/data.dcp, Launchpad/Textures/*.eti, etc. You've already extracted this.

PACK_EE.PAK — game data packed for the Emotion Engine (main CPU).

PACK_IOP.PAK — game data packed for the I/O Processor.

Not relevant:

.PSS files (video streams).

ARABIC.PAK, ENGLISH.PAK, etc. (language packs).

Most of MODULES/ — the generic PS2 OS modules (network, sound, controllers).

🛠️ The Reverse-Engineering Path
Priority 1: Find the cn2ncd decoder in SCRM202.IRX.

The SCRM202.IRX file is your strongest lead. Its name suggests "scramble 202" — a cryptographic/scrambling module. In PS2 homebrew, .irx modules run on the IOP and expose functions via an export table. The decoder used by Digimask for the cn2ncd XOR and the subsequent zlib decompression is very likely implemented here.

Here's how to attack it:

bash
# Check what SCRM202.IRX actually is
file CAMEO/MODULES/SCRM202.IRX
strings -n 6 CAMEO/MODULES/SCRM202.IRX | head -50
strings -n 6 CAMEO/MODULES/SCRM202.IRX | grep -i -E "cn2ncd|sdz|decrypt|scramble|zlib" 
If SCRM202.IRX contains the string cn2ncd, you've struck gold. Load it into Ghidra and find the function referencing that string. It will be the XOR loop.

Priority 2: Trace the model generation in SCES_524.26.

Once you find the decoder, you need to find where the game calls it during the Cameo process. Load SCES_524.26 into Ghidra (with the Emotion Engine extension) and:

Search for the strings HDIG, HDIF, base_27062004, female_base_06_03_02.

Find cross-references. Those will point to the function that loads the base head models.

Look for the string VTXANVRT — this is the marker for the vertex section in the .dmk format. The code that reads it will show you the exact parsing logic for the head mesh.

Search for EGMI — the .eti magic. The function that reads it will show you the palette layout and pixel format, which is your blocker for the textures.

Priority 3: Use the .irx export tables to understand the API.

.irx files have a header with exported function names. Use ps2-irx-tool or just strings to see what's exported:

bash
strings -n 4 CAMEO/MODULES/SCRM202.IRX | grep -E "^[a-z_]{4,}$" | head -40
That will show you function names like sceScrmDecode, sceScrmInit, etc. — giving you the exact API surface to look for.

# - file type detection

echo

        file "$f"
    done
    for f in "$OUT/cameo_modules/"*; do

grep -n -i -E "digimask|cn2ncd|VTXANVRT|TRIANTRI|HDIG|HDIF|EGMI" "$MAIN_STRINGS" 2>/dev/null | head -40 > "$OUT/recon/main_elf_marker_context.txt" || true

# ---------------------------------------------------------
SUMMARY="$OUT/recon/SUMMARY.txt"

🧬 What "Not Stripped" Means
When a PS2 game executable is not stripped, the symbol table is preserved. That means every single function, class, and global variable has its original name in the binary. Instead of seeing:

text
sub_8004A3B0:
    addiu sp, sp, -0x20
    ...
You see:

text
DigimaskMeshData::AddDigimaskHead(unsigned char &, char const*, int, void const*, unsigned int, ...)
    addiu sp, sp, -0x20
    ...
That's the difference between guessing what a function does and knowing.

🔍 What You're Looking For in AddDigimaskHead
The AddDigimaskHead function should contain:

The XOR key cn2ncd loaded as a constant, or generated.

A call to zlib's inflate function (or a custom equivalent).

The IndexError on all four codecs at all four offsets means the byte stream doesn't match any of those formats' grammar. If it were LZSS, LZ4, or LZF, at least one of those decoders would produce some output before hitting a boundary — even if garbage. That rules out the standard LZ family. The cn2ncd codec is something else.

What we've definitively learned about cn2ncd
Not simple XOR — tried 6 keys, none produced readable output.

Not nibble-swap, not bit-reverse, not add/sub — all scored near zero on float plausibility.

Not LZSS, not LZ4, not LZF — all decoders crashed on the first token.

Not a plain u16/u32 index array — scores are similar across all offsets (the metric doesn't discriminate).

The one thing we haven't used: the code table
Recall from way back: at PACK_EE.PAK offset 0x191726c sits the table:

text
????CREAENHASCACV3ACQUACSONDBOWANRMAPNTATXCAMEMBFPCOPXLTMATLAPPETHMBTRIMTRIMITRMPROGMSHTSHPEGRPT
I dismissed it as possibly a localization table. Let me revisit that dismissal. The structure:

50 two-character codes

Repeats: AC appears 3×, TR 2×, IM 2×, MA 2×, MB 2×, PE 2×

???? at the start

Repeated codes mean it's not a Huffman table (Huffman codes are unique). It's a substitution dictionary — a set of token pairs the codec replaces on output.

The ???? at the start is likely the escape prefix. When the decompressor sees ???? (four 0x3F bytes) in the compressed stream, the next 2 bytes are literal. Otherwise, 2 bytes are looked up in the table and replaced.

That's exactly the grammar of a digraph substitution codec, and it explains why none of the LZ-family decoders matched: they don't use this table.

The right test
Try the digraph substitution on the payload. But — the table is only 100 bytes, which is not enough for a full 2-byte codebook (65536 possible pairs). So either:

A — The table is a partial dictionary: only the 50 most common pairs are substituted, everything else is literal. Compressed data stores only the substituted pairs plus escapes. This is more like a token substitution where common pairs get 1-byte codes (fit 50 into 256 byte values).

B — The table is a rotation/permutation seed: it generates a 256-entry decoding map procedurally.

C — The table is unrelated to the codec. It's a runtime string pool for the SDK's menu (each token is a menu item name abbreviation).

I think C is most likely given the table contains only English-friendly pairs like CR, EA, EN, HA, SC, AC, QU, SO, ND, BO, WA, MA, PN, TA, ME, MB, PE, TH, TR, IM, IT, RM, PR, OG, MS, HT, SH, GR, PT. Those are English digrams (common 2-letter combinations), and they'd only be useful for compressing English text — which the .dmk file is not.

So the table is probably not the codec. It's an SDK-internal English text compression table used elsewhere.

You found the ApeEscapeRecomp project by mstan. It's a very different animal from the THPS2 decomp you were looking at, and worth understanding because it points to a class of tools that could apply to your Digimask work.

What this actually is
ApeEscapeRecomp is a static recompilation project, not a decompilation.

Decompilation = someone reads the disassembly and writes equivalent C/C++ source. The output is human-readable, maintainable, and modifiable. THPS2-demo-decomp is this.

Static recompilation = a tool reads the MIPS machine code and mechanically translates it into equivalent C. The output is machine-generated and functionally identical, but not human-readable source. ApeEscapeRecomp is this.

The framework, PSXRecomp (by mstan), takes a PS1 disc image and produces a native PC executable via:

Ghidra-derived function seeds (seeds/)

An AOT (ahead-of-time) MIPS → C translator

Compiled native code that runs on a simulated PS1 (GPU, SPU, GTE, memory cards, and a real recompiled BIOS)

It has 47 archive overlays precompiled from the original disc. Not a decompilation.

Why this matters for your Digimask work
It doesn't directly help with Digimask — Ape Escape is PS1, and Digimask is PS2. Different architectures. PSXRecomp handles MIPS-I (R3000A) PS1 code, not MIPS-III (R5900) PS2 code.

But the framework concept applies. If PSXRecomp existed for PS2, it would:

Statically translate SCES_524.26's MIPS code into a native executable

Include the DMSDK overlay code if it exists on the disc

Run the game natively, letting you debug the Digimask path at the C level

The PS2 equivalent would be a framework like PCSX2's recompiler or a similar AOT tool. There's no public PS2Recomp that I'm aware of at the ApeEscapeRecomp level.

#!/usr/bin/env python3
"""dmk_analyze.py — full entropy and structure scan of a .dmk file."""

import struct
import sys
import math
from collections import Counter

def entropy(chunk):
    if not chunk:
        return 0.0
    c = Counter(chunk)
    n = len(chunk)
    return -sum((v/n) * math.log2(v/n) for v in c.values())

def main(path):
    data = open(path, "rb").read()
    N = len(data)
    print(f"file: {path}")
    print(f"size: {N} bytes")
    print()

    # Block entropy, 256-byte blocks
    print("=== Entropy per 256-byte block (first 8 KB) ===")
    print(f"{'offset':>10}  {'entropy':>8}  {'ascii':>64}")
    for off in range(0, min(N, 8192), 256):
        block = data[off:off+256]
        e = entropy(block)
        asc = ''.join(chr(b) if 32 <= b < 127 else '.' for b in block[:64])
        print(f"0x{off:08x}  {e:>8.3f}  {asc}")
    print()

    # Look for periodic patterns at strides 4..64
    print("=== Self-similarity at various strides ===")
    for stride in [4, 8, 12, 16, 20, 24, 32, 48, 64]:
        matches = 0
        checks = 0
        for i in range(0, min(N - stride * 4, 65536), 4):
            if data[i:i+4] == data[i+stride:i+stride+4]:
                matches += 1
            checks += 1
        if checks:
            print(f"  stride {stride:3}: {matches:6}/{checks:6}  ({100*matches/checks:.1f}% match)")
    print()

    # Zero-run analysis
    print("=== Long runs of identical bytes ===")
    runs = []
    i = 0
    while i < N:
        j = i
        while j < N and data[j] == data[i]:
            j += 1
        if j - i > 32:
            runs.append((i, j - i, data[i]))
        i = j if j > i else i + 1
    for off, length, byte in runs[:30]:
        print(f"  0x{off:08x}  {length:>6} bytes of 0x{byte:02x}")
    print(f"  total: {len(runs)} long runs")
    print()

    # Byte frequency
    c = Counter(data)
    print("=== Most common bytes ===")
    for byte, count in c.most_common(20):
        print(f"  0x{byte:02x}  {count:>10}  ({100*count/N:.2f}%)")
    print()

    # Bigram frequency (adjacent pairs)
    print("=== Most common 2-byte sequences ===")
    bg = Counter()
    for i in range(0, N - 1, 2):
        bg[data[i:i+2]] += 1
    for pair, count in bg.most_common(20):
        print(f"  {pair.hex(' ')}  {count:>10}")
    print()

    # Look for structural signatures
    print("=== Structural signatures ===")
    sigs = {
        "SDZ\\0": b"SDZ\x00",
        "cn2ncd": b"cn2ncd",
        "cn2nc": b"cn2nc",
        "0xff * 8": b"\xff" * 8,
        "0x00 * 8": b"\x00" * 8,
        "float 1.0 BE": b"\x3f\x80\x00\x00",
        "float 1.0 LE": b"\x00\x00\x80\x3f",
        "float 0.0": b"\x00" * 4,
    }
    for name, pattern in sigs.items():
        positions = []
        i = 0
        while True:
            p = data.find(pattern, i)
            if p < 0:
                break
            positions.append(p)
            i = p + 1
            if len(positions) > 50:
                break
        if positions:
            print(f"  {name:15}: {len(positions)} hits, first 5 at "
                  f"{['0x%x'%p for p in positions[:5]]}")

What not to do
Don't keep running the same scans on the same bytes with slightly different parameters. We've done enough of that.

Don't keep reading decompilation lists. They're reference material, not tools.

Don't disassemble more of SCES_524.26. We've established the code isn't there.

Don't guess at format layouts from hexdumps alone. The analyzer will tell us factually.

Run the analyzer. Then we go from there. If it shows a compressed region, we work on decompressing that. If it shows plain structured data, we parse it. Either way, we stop guessing.
